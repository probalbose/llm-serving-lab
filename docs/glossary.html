LLM Serving Glossary

Terms used in llm-serving-lab. They are standard across LLM inference, vLLM, llama.cpp and the monitoring stack. Each entry gives the short name, the full name, what it means and a worked example.

Latency and throughput metrics

TTFTTime To First Token

Time from sending the request until the first generated token arrives. It covers network, queueing and prefill, so it grows with prompt length and with load. For a chat user, this is how long the reply takes to start.

Example: sent at 0.000 s, first content chunk at 0.500 s, so TTFT = 500 ms. A 38-token prompt on the M4 Max took 271 ms of prefill on its own.

ITLInter-Token Latency

The gap between each pair of consecutive output tokens, kept as a list. It shows individual stalls, so it is the metric for tail smoothness (p99). Users feel ITL as a stream that stutters or pauses.

Example: tokens at 0.500, 0.520, 0.540, 0.640 and 0.660 s give ITL = [20, 20, 100, 20] ms. The 100 ms stall is visible here but disappears in an average.

TPOTTime Per Output Token

One number per request: the mean decode time per token after the first, (t_last − t_first) / (n − 1). It divides by n − 1 because n tokens have n − 1 gaps, and the first token's wait is already in TTFT. Its reciprocal is the token rate one user sees.

Example: (0.660 − 0.500) / 4 = 40 ms, which is 25 tok/s. llama-server reported predicted_per_token_ms: 13.96, so 1000 / 13.96 ≈ 72 tok/s.

Some tools call this ITL; vLLM's benchmark reports both, so check which definition a number uses.

E2EEnd-to-End latency

Time from sending the request to receiving the last token: the whole wait. It decomposes as E2E = TTFT + TPOT × (n − 1), so long answers are dominated by decode speed and short ones by TTFT.

Example: 500 + 40 × 4 = 660 ms. For a 500-token answer with TTFT = 300 ms and TPOT = 14 ms: 0.3 + 0.014 × 499 ≈ 7.3 s.

tok/sThroughput (output tokens per second)

Total tokens the server generates per second across all requests. It differs from per-user speed: batching raises total throughput while each user's TPOT gets slightly worse.

Example: 1 user at 72 tok/s = 72 tok/s total. 4 users at 55 tok/s each = 220 tok/s total. The server got 3× more productive while each user got about 25% slower.

RPS / QPSRequests (or Queries) Per Second

Request arrival rate, written λ (lambda) in queueing maths. It is the load you apply in a load test. For LLMs it means little without the prompt and output lengths, because one request can be 10 tokens or 10,000.

Example: 2 RPS of 200-token answers = 400 output tok/s needed. If the server peaks at 220 tok/s, the queue grows without bound.

GoodputGoodput (throughput that meets the SLO)

Requests per second that complete and meet every SLO target. Raw throughput can keep rising while latency gets unacceptable; goodput peaks and then falls. It is the honest capacity number.

Example: in 60 s, 100 requests complete but only 80 meet TTFT < 500 ms and TPOT < 50 ms. Throughput = 1.67 req/s, goodput = 1.33 req/s.

SLI / SLO / SLAService Level Indicator / Objective / Agreement

SLI is the thing you measure, SLO is the internal target for it, and SLA is the external promise with consequences. The SLO is usually stricter than the SLA so you get warned before breaching it.

Example: SLI = p95 TTFT. SLO = p95 TTFT < 500 ms over 28 days. SLA = p95 TTFT < 1 s or the customer gets credits.

p50 / p95 / p99Percentiles (50th, 95th, 99th)

The value below which 50%, 95% or 99% of observations fall. p50 is the typical case; p99 is the tail that one in a hundred users hits. Latency SLOs use percentiles because means hide the tail.

Example: 100 TTFTs sorted, p99 is roughly the 99th value. If 98 are 300 ms and 2 are 4 s, the mean is 374 ms (looks fine) but p99 = 4 s.

Error budgetError budget

The amount of SLO failure you are allowed: 1 − SLO target. When it is spent, risky changes stop until reliability recovers.

Example: 99.5% of requests must meet the TTFT SLO. At 1 M requests per month, the budget is 5,000 slow or failed requests.

KneeLatency knee (saturation point)

The load where latency stops being flat and starts climbing steeply, because the server is saturated and requests queue. Safe operating load sits below the knee with headroom.

Example: llama-server has n_slots = 4. Expect TTFT to stay roughly flat up to 4 concurrent requests, then jump once new requests have to wait for a free slot. Stage 2 measures where it actually happens.

How inference works

TokenToken

The unit a model reads and writes: a word piece produced by the tokenizer. Prices, context limits and speed are all counted in tokens, not characters or words.

Example: in English, 1 token ≈ 0.75 words, about 4 characters. "Explain a KV cache in 3 sentences" plus the chat template became 38 prompt tokens.

PrefillPrefill (prompt processing)

The first phase: the model processes all prompt tokens in parallel in one forward pass and fills the KV cache. It is compute-bound (big matrix multiplies) and sets most of TTFT.

Example: a 4,000-token prompt prefills much faster per token than a 38-token one, because the GPU can use its compute fully. Prefill time still grows roughly linearly with prompt length.

DecodeDecode (generation)

The second phase: tokens are generated one at a time, each needing a full pass over the weights. It is memory-bandwidth-bound, because every step reads all weights to produce one token per sequence.

Example: Qwen2.5-7B Q4_K_M is about 4.7 GB. At 410 GB/s the ceiling is about 410 / 4.7 ≈ 87 tok/s; we measured 72 tok/s, about 82% of the limit.

AutoregressiveAutoregressive generation

Each new token depends on all previous tokens, so generation is inherently sequential within one request. This is why decode can't be parallelised across a single answer and why batching across requests matters.

Example: to write token 5, the model must already have tokens 1 to 4. 200 tokens means 200 sequential decode steps.

Logits / samplingLogits and sampling (temperature, top-p, top-k)

The model outputs a score (logit) for every vocabulary token; sampling turns these into a choice. Temperature sharpens or flattens the distribution, top-k keeps the k best, top-p keeps the smallest set whose probability sums to p.

Example: temperature 0 always picks the top token (deterministic, good for benchmarks). Temperature 0.8 with top_p 0.95 gives varied text. Use temperature 0 or a fixed seed when comparing runs.

n_ctxContext window / context length

The maximum number of tokens (prompt plus output) a sequence can hold. Longer context costs KV cache memory linearly and attention compute more than linearly.

Example: llama-server logged n_ctx_slot = 32768: each of its 4 slots can hold a 32k-token conversation.

max_tokensMaximum output tokens

Request parameter capping how many tokens the server will generate. Generation stops at this cap or at an end-of-sequence token, whichever comes first (finish_reason = "length" or "stop").

Example: max_tokens: 256 with a model that wants to write 400 tokens returns 256 and finish_reason: "length". Benchmarks often fix output length so runs are comparable.

Chat templateChat template

The model-specific text format that wraps messages with role markers before tokenizing. The server applies it, which is why the prompt token count is larger than your message.

Example: Qwen wraps a user message as <|im_start|>user … <|im_end|> plus a default system prompt, turning 7 words into 38 tokens.

Memory: weights, KV cache, quantisation

KV cacheKey-Value cache

Stored attention keys and values for every token already processed, so decode doesn't recompute them. It grows with tokens × concurrent sequences and is usually what limits how many requests fit on a GPU. Size per token = 2 × layers × KV heads × head dim × bytes per value.

Example: Qwen2.5-7B has 28 layers, 4 KV heads, head dim 128. In fp16: 2 × 28 × 4 × 128 × 2 B = 57,344 B ≈ 56 KB per token. One 32k-token sequence ≈ 1.8 GB; four of them ≈ 7.3 GB.

GQA / MQAGrouped-Query / Multi-Query Attention

Attention variants where several query heads share one key/value head. Fewer KV heads means a much smaller KV cache and less memory traffic during decode, with little quality loss.

Example: Qwen2.5-7B has 28 query heads but only 4 KV heads, so its KV cache is 7× smaller than full multi-head attention would need.

PagedAttentionPagedAttention (paged KV cache)

vLLM's core idea: store the KV cache in fixed-size blocks, like OS memory pages, instead of one contiguous buffer per request. It removes fragmentation, so far more sequences fit and blocks can be shared between requests.

Example: with block size 16, a 1,000-token sequence uses 63 blocks and wastes at most 15 token slots. A contiguous pre-allocation of 32k tokens would waste 31k.

Prefix cachingAutomatic prefix caching

Reusing KV cache blocks when a new request starts with the same tokens as an earlier one, so that part of prefill is skipped. Big wins for shared system prompts, few-shot examples and multi-turn chat.

Example: 1,000 requests share a 2,000-token system prompt. With prefix caching only the first pays that prefill; the rest start from cache and TTFT drops sharply. llama.cpp shows this as cache_n in its timings.

gpu_memory_utilizationvLLM GPU memory fraction

Fraction of GPU memory vLLM may use (default 0.9). After loading weights, the remainder becomes KV cache, which caps how many sequences can run at once.

Example: L4 with 24 GB × 0.9 = 21.6 GB. A 7B model in fp16 takes about 15 GB, leaving roughly 6 GB of KV cache, about 110k tokens at 56 KB each.

QuantisationQuantisation (INT8, INT4, FP8)

Storing weights (and sometimes the KV cache) in fewer bits. Smaller weights mean less memory and less data to read per decode step, so decode gets faster, at some cost in quality.

Example: a 7B model is about 14 GB in fp16 (2 bytes per parameter) and about 4.7 GB in Q4_K_M (about 4.8 bits per parameter). Decode ceiling at 410 GB/s goes from about 29 to about 87 tok/s.

GGUF / Q4_K_MGGUF file format / 4-bit K-quant, medium

GGUF is llama.cpp's single-file model format holding weights, tokenizer and metadata. Q4_K_M is one of its quantisation schemes: mostly 4-bit blocks with some layers kept at higher precision, a common quality and size balance.

Example: bartowski/Qwen2.5-7B-Instruct-GGUF:Q4_K_M is the 7B Qwen instruct model, quantised to Q4_K_M, from the "bartowski" Hugging Face repo.

GPU servers like vLLM usually use AWQ, GPTQ or FP8 checkpoints instead of GGUF.

Batching and scheduling

Batch sizeBatch size (concurrent sequences)

How many sequences the server advances together in one forward pass. Decode reads the weights once per step regardless of batch size, so batching multiplies throughput almost for free until compute or KV memory runs out.

Example: one step reads 4.7 GB of weights. At batch 1 that yields 1 token; at batch 8 it yields 8 tokens for nearly the same time.

Static batchingStatic (request-level) batching

Collect a batch, run it until every sequence finishes, then start the next batch. Short answers wait for the longest one, and new arrivals wait for the whole batch, so GPU time is wasted.

Example: a batch has answers of 20 and 500 tokens. The 20-token request finishes early, but its slot sits idle for 480 more steps.

Continuous batchingContinuous (iteration-level) batching

The scheduler re-forms the batch on every decode step: finished sequences leave immediately and waiting requests join. This is how vLLM, TGI and llama.cpp (with slots) keep the GPU busy.

Example: the 20-token request leaves at step 20 and a queued request takes its place at step 21. Throughput can be several times higher than static batching.

max_num_seqsvLLM maximum concurrent sequences

vLLM's cap on sequences running in one batch. Higher raises throughput but each step takes longer, so TPOT rises; beyond the KV cache limit, sequences get preempted.

Example: sweeping max_num_seqs over 8, 32, 128 and 256 while measuring goodput is one of the Stage 4 experiments.

max_num_batched_tokensvLLM token budget per step

The maximum number of tokens (prefill plus decode) processed in one scheduler step. It bounds how much prefill can be squeezed in alongside decodes, trading TTFT against ITL.

Example: budget 2,048 with 64 decoding sequences leaves room for 1,984 prefill tokens in that step.

Chunked prefillChunked prefill

Splitting a long prompt's prefill into chunks spread across several steps, mixed in with ongoing decodes. Without it, one long prompt stalls every other user's next token.

Example: a 16k-token prompt arrives. Unchunked, all running streams freeze for about a second (an ITL spike). Chunked into 2k-token pieces, they slow slightly over 8 steps instead.

Slotllama.cpp server slot

llama-server's fixed number of parallel sequences (-np / --parallel), each with its own context. Requests beyond the slot count wait in a queue.

Example: our run showed n_slots = 4. A 5th concurrent request queues until a slot frees, which shows up as extra TTFT.

PreemptionPreemption (swap or recompute)

When the KV cache fills, the scheduler evicts a running sequence and later swaps its cache back or recomputes it. It keeps the server alive but causes large latency spikes for the victim.

Example: vLLM logs a preemption warning and the metric vllm:num_preemptions_total rises. A sustained rise means too much concurrency for the KV memory.

HOL blockingHead-of-line blocking

A slow item at the front of a queue delays everything behind it. In LLM serving it is typically one huge prompt or a long generation holding resources others need.

Example: a 30k-token prompt arrives first; ten short chat requests behind it all see multi-second TTFT. Chunked prefill and fair scheduling reduce this.

Hardware and performance limits

Memory bandwidthMemory bandwidth (HBM / unified memory)

Bytes per second the processor can read from memory. It sets the decode ceiling: tokens per second per sequence ≤ bandwidth ÷ bytes read per step (mostly the weights).

Example: M4 Max (36 GB) about 410 GB/s, L4 about 300 GB/s, H100 SXM about 3.35 TB/s. A 7B fp16 model (14 GB) on H100: 3,350 / 14 ≈ 240 tok/s ceiling at batch 1.

FLOPSFloating-point operations per second

Compute throughput. A forward pass costs about 2 FLOPs per parameter per token, which sets the prefill ceiling.

Example: 7B model, 4,000-token prompt: 2 × 7e9 × 4,000 = 5.6e13 FLOPs. On an H100 at about 989 TFLOPS dense BF16 that is about 57 ms at 100% efficiency; real-world is perhaps 2 to 3× that.

AIArithmetic intensity

FLOPs performed per byte moved from memory. Low intensity means memory-bound; high means compute-bound. The crossover is the hardware's ridge point = peak FLOPS ÷ bandwidth.

Example: decode at batch 1 in fp16: about 2 FLOPs per 2 bytes, intensity ≈ 1. H100 ridge ≈ 989e12 / 3.35e12 ≈ 295. So decode is far below the ridge (memory-bound), and batching raises intensity roughly in proportion to batch size.

RooflineRoofline model

A plot of achievable performance against arithmetic intensity: a sloped "memory roof" then a flat "compute roof". It tells you which resource limits a workload and how far you are from the ceiling.

Example: our decode run hit 72 of a possible 87 tok/s on the memory roof, 82% efficiency, so the remaining gain from software tuning at batch 1 is small.

MBU / MFUModel Bandwidth Utilisation / Model FLOPs Utilisation

Achieved bandwidth or FLOPS as a fraction of hardware peak. MBU is the right efficiency number for decode, MFU for prefill and training.

Example: MBU = (4.7 GB × 72 tok/s) / 410 GB/s ≈ 83%. That's a good number to quote with the hardware named.

Memory-bound vs compute-boundMemory-bound vs compute-bound

Whether a workload waits on data movement or on arithmetic. Decode at small batch is memory-bound; prefill and large-batch decode are compute-bound. The fix differs: quantise or batch for memory-bound, faster kernels or more GPUs for compute-bound.

Example: doubling batch size from 1 to 2 nearly doubles decode throughput (memory-bound). Doubling prompt length nearly doubles prefill time (compute-bound).

Parallelism across GPUs

TPTensor Parallelism

Split each layer's weight matrices across GPUs; every GPU computes part of every layer and they exchange results each layer. It cuts per-GPU memory and latency but needs fast interconnect (NVLink).

Example: a 70B fp16 model (140 GB) doesn't fit on one 80 GB H100. With --tensor-parallel-size 2 each GPU holds about 70 GB of weights.

PPPipeline Parallelism

Split the model by layers: GPU 1 runs layers 1 to 40, GPU 2 runs 41 to 80. Less communication than TP, so it works across nodes, but each request passes through stages in sequence.

Example: a model too large for one 8-GPU node runs with TP 8 inside each node and PP 2 across two nodes.

DPData Parallelism (replicas)

Run independent full copies of the model and load-balance requests between them. Throughput scales linearly; per-request latency doesn't change. This is the usual way to scale serving horizontally.

Example: one replica sustains 3 req/s within SLO. To serve 10 req/s with headroom, run 4 replicas behind a load balancer.

EP / MoEExpert Parallelism / Mixture of Experts

MoE models have many expert sub-networks but route each token to only a few, so compute per token is small while total weights are large. EP places different experts on different GPUs.

Example: a model with 8 experts and top-2 routing has all 8 experts' weights in memory but runs only 2 per token, about a quarter of the expert compute.

Decoding speedups

Spec decodingSpeculative decoding

A small draft model (or n-gram lookup) proposes several tokens; the large model verifies them all in one forward pass and keeps the accepted prefix. Output is identical to normal decoding, but fewer expensive steps are needed when guesses are good.

Example: the draft proposes 4 tokens and 3 are accepted, so one big-model pass yields 4 tokens (3 accepted plus 1 corrected) instead of 1.

Acceptance rateSpeculative acceptance rate

Fraction of draft tokens the target model accepts. Speed-up depends on it: low acceptance wastes draft compute and can make things slower, especially at high batch sizes where the GPU is already busy.

Example: 70% acceptance on code completion gives a clear win; 30% on creative writing may be slower than no speculation.

FlashAttentionFlashAttention

An attention kernel that computes attention in tiles held in fast on-chip memory, never writing the full attention matrix to HBM. Same result, far less memory traffic, which matters most for long prompts.

Example: for a 32k-token prompt the full attention matrix per head would be 32k × 32k; FlashAttention never materialises it, so long-context prefill gets much faster and fits in memory.

CUDA graphsCUDA graphs

Recording a sequence of GPU kernel launches once and replaying it, removing CPU launch overhead. It matters for decode, where each step is small and launch overhead can dominate.

Example: vLLM captures graphs for common batch sizes at startup (this is part of its warm-up time). --enforce-eager disables them, useful for debugging but slower.

Load testing and queueing

Closed-loopClosed-loop load generator

N virtual users, each sending the next request only after the previous one finishes. When the server slows down, the load automatically drops, so it hides overload and underestimates latency.

Example: 10 users. If latency rises from 1 s to 5 s, the offered load silently drops from 10 to 2 req/s.

Open-loopOpen-loop load generator

Requests are sent on a schedule regardless of whether earlier ones finished, like real users who don't coordinate. This is the correct way to find the knee. Stage 2 builds one.

Example: send at 5 req/s for 60 s. If the server can only do 3 req/s, the backlog grows and latency rises without limit, which is exactly what you need to see.

Poisson arrivalsPoisson arrival process

Arrivals that are independent and random at a constant average rate λ; the gaps between them are exponentially distributed with mean 1/λ. It's the standard model of many independent users.

Example: λ = 4 req/s gives a mean gap of 250 ms. In Python: random.expovariate(4.0) for each gap.

COCoordinated omission

A measurement bug where the load generator waits for slow responses before sending more, so it never records the requests that would have been delayed. Tail latencies look far better than reality.

Example: the server stalls for 2 s. A closed-loop client records one 2 s request. At a real 10 req/s, 20 requests would have arrived during the stall, with waits from 0 to 2 s.

Little's LawLittle's Law: L = λ × W

In a stable system, average number in the system (L) = arrival rate (λ) × average time each spends in it (W). It links concurrency, throughput and latency with no assumptions about distributions.

Example: 0.6 req/s with an average E2E of 7 s means about 4.2 requests in flight. With only 4 slots, a queue must form.

ρUtilisation (rho)

Fraction of capacity in use, λ ÷ service rate. Queueing delay grows like 1 / (1 − ρ), so it explodes as utilisation approaches 100%. This is why SREs keep headroom.

Example: at ρ = 0.5 queueing adds about 1× the service time; at 0.9 about 9×; at 0.99 about 99×.

Warm-upWarm-up period

Initial requests excluded from results because caches, kernels and graphs are still initialising. Including them distorts the numbers.

Example: our first llama-server request prefilled at 140 tok/s, which is cold-start speed. Discard the first 10 to 30 s of a run.

Serving software and protocols

vLLMvLLM inference engine

Open-source, high-throughput GPU inference server built around PagedAttention and continuous batching, with an OpenAI-compatible API and Prometheus metrics. The usual reference for production open-model serving.

Example: vllm serve Qwen/Qwen2.5-7B-Instruct --max-num-seqs 64 serves on port 8000 with metrics at /metrics.

llama.cppllama.cpp / llama-server

C/C++ inference engine optimised for CPUs and Apple Silicon (Metal), using GGUF models. llama-server is its HTTP server with an OpenAI-compatible API and slot-based concurrency.

Example: llama-server -hf bartowski/Qwen2.5-7B-Instruct-GGUF:Q4_K_M --port 8080, our local baseline.

MLXApple MLX

Apple's array framework for Apple Silicon, using unified memory. mlx-lm runs and serves LLMs on a Mac, often faster than llama.cpp for some models.

Example: comparing llama.cpp and MLX on the same model and quantisation on the M4 Max is a fair engine-versus-engine test.

SGLang / TGI / TRT-LLMSGLang, Text Generation Inference, TensorRT-LLM

Other production inference servers. SGLang is strong on prefix reuse (RadixAttention), TGI is Hugging Face's server, and TensorRT-LLM is NVIDIA's compiled, highly optimised engine.

Example: an interviewer may ask why you'd choose one over another: think throughput, hardware support, operational simplicity and features like structured output.

OpenAI-compatible APIOpenAI-compatible chat completions API

The de-facto HTTP interface: POST to /v1/chat/completions with a messages list. Because vLLM, llama.cpp and others all implement it, one client can benchmark them all.

Example: {"messages":[{"role":"user","content":"hi"}],"stream":true,"max_tokens":256}

SSEServer-Sent Events

A simple HTTP streaming format: the server keeps the response open and sends lines starting with data: , separated by blank lines. LLM servers use it to stream tokens as they are generated.

Example: data: {"choices":[{"delta":{"content":"KV"}}]} … then data: [DONE]. The first chunk often has only {"role":"assistant"} and the last has delta: {}; neither is a token.

ChunkStream chunk (SSE event)

One data: event in the stream. It usually carries one token's text, but servers may merge several tokens or send empty chunks, so chunk count is not token count.

Example: 71 tokens generated may arrive as 71 chunks on llama.cpp but fewer on a server that batches output. Use usage.completion_tokens for the true count.

finish_reasonFinish reason

Why generation ended: "stop" (end-of-sequence or stop string), "length" (hit max_tokens) or an error. Benchmarks should check it, because a run full of early stops measures something different.

Example: our curl run ended with "finish_reason":"stop" after 71 tokens.

Observability

PrometheusPrometheus

Time-series monitoring system that scrapes /metrics endpoints on an interval and stores counters, gauges and histograms, queried with PromQL.

Example: scrape vLLM every 5 s; alert when p95 TTFT over 5 minutes exceeds the SLO.

HistogramPrometheus histogram

Counts of observations in fixed buckets, which can be summed across servers and turned into approximate percentiles. Percentile accuracy depends on bucket boundaries.

Example: histogram_quantile(0.95, sum by (le) (rate(vllm:time_to_first_token_seconds_bucket[5m]))) gives fleet-wide p95 TTFT.

vLLM metricsKey vLLM server metrics

vLLM exports, among others: TTFT and per-token latency histograms, running and waiting request counts, KV cache usage and preemptions. Names change between versions, so check /metrics on your build.

Example: vllm:num_requests_waiting rising while KV cache usage sits near 100% means you are memory-limited: lower max_num_seqs, quantise or add replicas.

DCGMNVIDIA Data Center GPU Manager

NVIDIA's GPU telemetry; dcgm-exporter exposes it to Prometheus. Key signals: GPU utilisation, memory used, SM activity, power, temperature, XID errors.

Example: "GPU util 100%" only means a kernel was running; SM activity and tensor-core activity show whether it was doing useful work.

Client vs server metricsClient-side vs server-side measurement

The server measures from when it received the request; the client measures what the user experienced, including network, TLS, load balancer and queueing in front of the server. SLOs should be judged on the client view.

Example: if the server reports 271 ms of prefill but your client measures 310 ms TTFT, the 39 ms gap is HTTP, queueing and tokenisation that server metrics cannot see. Stage 1 prints both so you can measure the real gap.
